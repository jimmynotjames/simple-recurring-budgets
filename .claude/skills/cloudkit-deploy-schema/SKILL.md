# Deploy CloudKit schema to Production

A narrow, safety-first skill for one task: getting this app's CloudKit schema (record types, fields, indexes; never data) from Development into Production. TestFlight and App Store builds use Production (`docs/tech-design-doc.md` §4.3), so an undeployed or wrong schema makes sync fail silently for exactly those builds, with no visible error to the user.

Be conservative. Production schema changes are practically one-directional and permanent: fields can be added at any time but cannot be deleted once deployed (`docs/tech-design-doc.md` §4.3). A careless deploy bakes in cruft forever. Slow down for every deploy, the first and every later one.

## Model preference

Run this skill on the latest Opus-tier model (or its contemporary equivalent), not Sonnet. Unlike the mechanical checklist-walking in `appstore-prepare-for-release` (deliberately Sonnet), this skill's whole job is judgment: whether a schema diff is intentional or stale cruft, whether a field removed from the Swift model was ever synced to Development, and whether an action is the safe direction or the destructive one. A wrong call permanently mutates a production system serving real users (the same rationale as `appstore-prepare-for-release`'s P1.6/P1.7/P1.8/P6.1 escalations, which this skill supersedes for schema work at P3.7). If invoked from a Sonnet-orchestrated session (e.g. mid-checklist), run this skill's work on an Opus subagent instead of inline.

## Hard rules

- Never treat this as fire-and-forget. Every step that writes anything (Reset Environment, Deploy Schema Changes, `cktool import-schema` to either environment) requires an explicit, freshly stated human confirmation immediately before running, even if the user approved the overall plan earlier. Re-confirm at the point of action.
- "Reset Environment" and "Deploy Schema Changes" are opposite directions; never conflate them.
  - **Reset Environment** (Development only) wipes Development's schema and data back to match whatever is currently in Production. If Production is empty or behind Development, this destroys Development's working state.
  - **Deploy Schema Changes** (Development → Production) is additive-only: it pushes Development's current schema to Production and never touches data in either direction.
  - Before either action, tell the user which direction you believe you're going and why, and get their explicit go-ahead.
- Never hand-author or hand-edit a CKSL (`.ckdb`) file's field types from guesses about how SwiftData encodes a property. SwiftData's CloudKit mirroring has its own internal encoding (e.g. for `Decimal`, optional arrays, nested `Codable` structs) that isn't safe to reverse-engineer. The source of truth for what the schema should contain is the Development schema generated by the app's own real persistence code, never a hand-typed schema file.
- Data and schema are separate stores. Clearing or reviewing Development data has no effect on what a schema deploy pushes to Production, and vice versa. Don't conflate a data-hygiene concern with a schema-deploy concern.
- The CloudKit Console's "Deploy Schema Changes" button is the only way to promote a schema to Production; there is no `cktool` equivalent. `cktool import-schema` accepts `--environment production` as a syntactically valid value (Apple's man page lists it without caveat), but the server rejects it at request time: `BadRequestException: endpoint not applicable in the environment 'production'` (confirmed empirically; trust what the API does over the flag's accepted-values list). `import-schema` only works against `--environment development`. Budget for a manual Console click at the deploy step every time; don't script around it.

## Preflight checks (every invocation)

Run these before touching anything, and report the results before asking for any confirmation:

1. **Identify the container and team.** Read `com.apple.developer.icloud-container-identifiers` from `simple-recurring-budgets/Resources/simple_recurring_budgets.entitlements` for the container id. The team id comes from the Apple Developer account in use (ask the user if it isn't obvious from `fastlane/.env` or Xcode settings).
2. **Confirm `cktool` auth.** Schema management commands need a Management Token (different from the ASC API key used elsewhere in this repo):
   ```bash
   xcrun cktool save-token --type management
   ```
   This is interactive (opens a browser/prompts for the token). If not already authenticated, tell the user to run it themselves; don't script around it.
3. **Snapshot both environments before changing anything:**
   ```bash
   xcrun cktool export-schema --team-id <TEAM> --container-id <CONTAINER> --environment development --output-file tmp/schema-dev.ckdb
   xcrun cktool export-schema --team-id <TEAM> --container-id <CONTAINER> --environment production --output-file tmp/schema-prod.ckdb
   ```
   Show the user a summary of each (record types present, field counts) and the diff between them. This is your evidence base; read the current state rather than asking the user to recall it.
4. **Full bidirectional model-vs-schema field audit. Mandatory before every deploy.** Cross-reference the Development schema (exported above) against the current Swift model source (`simple-recurring-budgets/Models/*.swift`) in both directions and present a table (one row per `@Model` class):
   - **Stale fields** (in the CloudKit schema, absent from the current model): candidates for removal from Development before deploying; see "Handling stale fields". Don't rely on memory of what used to exist; `git log -p -- path/to/Model.swift` is the authoritative record.
   - **Missing fields** (a stored property on the current model with no corresponding `CD_<field>` in the exported Development schema): no non-nil value was ever written for it in whatever generated the current Development data, so CloudKit never created it, and it will silently be absent from Production if you deploy now. This is the more dangerous direction because it shows up as an absence, not a diff. Block the deploy and go back to generating more complete Development data (Recipe A step 2, or the equivalent regeneration for Recipe B) until every stored property has a field.
   - List "current model" properties directly from each `@Model` class's stored properties (`var`/`let` declarations that aren't computed), not from memory or from what a test/preview happens to touch. Exclude the model's own to-many relationship arrays from the "should appear on this record type" expectation: SwiftData represents a to-many relationship via the inverse foreign key (`CD_<parentType>`) on the child record type, not as a field on the parent. Confirm each relationship's inverse key is present on the child type.
   - Audit every `@Model` class in the schema's `models` array (check the `VersionedSchema` conformer, e.g. `SchemaV1.swift`, for the authoritative list), not just the ones that seem most relevant.

## Recipe

### A. First-ever ("greenfield") deploy for a container

Use when Production's schema is empty or near-empty (only Apple's built-in system record types, e.g. `Users`) and this is the first time this container's schema is being established.

1. Run the preflight checks. Confirm with the user that Production is empty/greenfield; don't assume it from an earlier conversation turn.
2. **Generate a complete, deterministic Development schema from real app code.** Don't rely on ad-hoc manual UI exercise, which risks missing a field. The reliable path:
   - Check whether a comprehensive fixture/seed routine already exists (e.g. `DebugData.seed(into:)` or equivalent; search for `#if DEBUG` seed helpers under `Models/` or `Previews/`). If one exists and its field coverage looks complete (cross-check against the current model's stored properties), reuse it.
   - Wire it to a throwaway trigger (a `#if DEBUG`-gated button, or a temporary call in the app-launch path) on a separate throwaway git branch that is never merged to main. Never commit temporary seed-wiring to a real feature branch or main.
   - Have the user run a plain Debug/Development-signed build (Xcode Run, simulator or physical device; what matters is Development code signing) signed into a real iCloud account with network on, and trigger the seed once.
   - Confirm the seed reached CloudKit (not just the local SwiftData store): ask the user to check the CloudKit Console's Development data browser for the new records, or re-run `export-schema --environment development` and confirm the expected record types/fields appear.
   - Keep the throwaway branch until the deploy is verified (step 5/7), in case the audit surfaces a gap and you need to re-seed.
3. Re-export the Development schema and re-run the full field audit from preflight check 4 (every model field must be confirmed present, not just "different from before"). Present the audit table and the diff against the empty Production baseline to the user. **Explicit confirmation required** before proceeding.
4. Deploy: tell the user to go to CloudKit Console → container → Schema → **Deploy Schema Changes**. This step is always manual; `cktool import-schema --environment production` is not an alternative (the API rejects it; see the hard rule). Have the user confirm once they've clicked through the Console's diff preview and committed.
5. Verify: `export-schema --environment production` again, and confirm it now matches Development's record types/fields.
6. Record what was deployed (record types, field count, date, method) in the release checklist snapshot's P3.7 item (see `docs/app-store-release-checklist.md`) and/or `docs/tech-design-doc.md` §4.3 if the constraint notes need updating.
7. **Clean up the throwaway branch now that the deploy is verified.** Confirm its only commits are the temporary seed-wiring (`git log --oneline main..<branch>`; check the diff touches only the throwaway trigger), then delete it:
   ```bash
   git branch -D <throwaway-branch>
   ```
   Use force-delete since it was deliberately never merged (plain `-d` refuses). If it was ever pushed, delete it on the remote too (`git push origin --delete <throwaway-branch>`), though it should have stayed local-only.

### B. Incremental deploy (schema already established in Production)

Use for any release after the first, when the SwiftData model has changed (new fields/record types) since the last deploy.

1. Run the preflight checks. The diff between the two exported schemas is the change set; present it to the user explicitly, field by field.
2. **If preflight check 4 flags any "missing fields"** (a new stored property with no field yet in Development; the normal case right after adding a field to an `@Model` class, before any record has been saved with a non-nil value for it), the Recipe A step 2 problem applies: don't guess, generate real data. Follow that step's method (reuse/extend a `#if DEBUG` seed fixture on a throwaway branch, run a Debug build signed into a real iCloud account, confirm the field materializes via a re-export) before proceeding. Skip only if the audit found no missing fields.
3. Confirm every new field in the diff is intentional (traces to an actual model change, not stale cruft); cross-check `git log` for the relevant model files if anything looks unexpected.
4. **Explicit confirmation required** before deploying, quoting the exact diff being promoted.
5. Deploy: tell the user to go to CloudKit Console → container → Schema → **Deploy Schema Changes** (always manual; see the hard rule).
6. Verify with a post-deploy `export-schema --environment production`.
7. Record the deploy in the current release's checklist snapshot P3.7 item.
8. If step 2 required a throwaway seeding branch, clean it up now per Recipe A step 7 (check its commits, then `git branch -D`).

## Handling stale fields in Development

If the preflight check finds Development schema fields with no corresponding property on the current model (e.g. a renamed or removed field from an earlier iteration):

- They can be deleted directly in the CloudKit Console (Development schema, unlike Production, supports field deletion). Confirm with the user which specific fields to remove, one by one, before doing so.
- Never use Reset Environment as a shortcut to clean up stale Development fields unless Production is confirmed empty/behind. Reset Environment wipes Development back to Production's current state, which is destructive if Production isn't already a superset of what you want to keep.
- Removing a stale field from Development doesn't affect Production unless it was already deployed there. If it was, it's stuck permanently (Production can't lose fields); just stop adding data to it going forward.

## Where this fits in a release

This skill is invoked from the App Store release checklist's P3.7 (`docs/app-store-release-checklist.md`, driven by `/appstore:prepare-for-release`). That item's Note should reference what this skill did (deploy method, fields involved, verification result) rather than duplicate the recipe.
